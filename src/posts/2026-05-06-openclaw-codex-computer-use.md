  <p class="meta">2026-05-06</p>
  <h1>OpenClaw + Codex Computer UseでジェネリックなエージェントをMacBook上で動かす</h1>

  <p>
    ここ数日は、OpenClaw の上でジェネリックなエージェントを動かしつつ、
    GUI 操作だけ Codex Computer Use にお願いする、という構成を試していた。
    やりたかったのはすごく素朴で、
    ふだんの会話やファイル編集はそのまま続けながら、
    必要なときだけブラウザや macOS アプリを触れるようにすることだった。
  </p>

  <p>
    この組み合わせ、実際やってみるとかなりしっくりくる。
    考える部分や普段の作業の本体は OpenClaw 側に置いて、
    「画面を見てクリックする」みたいなところだけを別経路で呼び出す感じ。
    こうしておくと、前段のモデルやエージェントが変わっても、
    GUI 操作だけは同じインターフェースで扱える。
    つまり特定のアプリに閉じない、かなりジェネリックなエージェントになる。
  </p>

  <h2>なぜ OpenClaw と Computer Use を分けたかったのか</h2>

  <p>
    最初から全部をひとつの GUI エージェントに寄せる方法もあるけれど、
    実際にやりたいことはもう少しばらけている。
    会話を覚えていてほしいし、ローカルのファイルも読みたいし、
    GitHub や Notion にもつなぎたい。
    でもその一方で、ブラウザの投稿欄を触るとか、
    サインイン画面のボタンを押すとか、
    そういう場面では視覚的な操作が必要になる。
  </p>

  <p>
    そこで OpenClaw を母艦にして、
    Computer Use を必要なときだけ呼び出す形にしてみると、
    エージェント全体の性格をかなり保ったまま、
    GUI 能力だけをふわっと差し込める。
    実際、普段のタスクは shell、memory、GitHub、Notion みたいなツールで進めて、
    詰まったところだけ Chrome を触る、という流れはすごく自然だった。
  </p>

  <h2>いちばん大きかった問題は、MacBook がすぐ寝ること</h2>

  <p>
    ただ、ここで現実が入ってくる。MacBook は放っておくと画面が消えるし、
    条件によってはロックもかかる。
    Computer Use はログイン後の GUI を前提にしているので、
    画面が暗いだけでもかなり不安定になる。
    実際、最初は Chrome が起動しているのに
    <code>cgWindowNotFound</code> で落ち続けた。
  </p>

  <p>
    このへん、雑に「スリープしてるからだめだった」とまとめると、
    あまり次につながらない。
    ロックされているのか、ディスプレイだけ寝ているのか、
    Mac 本体が寝ているのかで、詰まり方がそれぞれ違った。
    失敗をひとつの言葉でまとめすぎない方がよさそう、というのは、
    今回かなり実感したところだった。
  </p>

  <h2>SSH 経由で caffeinate を叩くと、ちゃんと前に進めた</h2>

  <p>
    いちばん効いたのは、Computer Use の前段に SSH を挟むことだった。
    Mac 側に制限付きの鍵を置いて、
    接続したら <code>caffeinate</code> だけを実行するようにした。
    具体的には、接続元では <code>ssh -T wake-rei</code> を叩くだけで、
    Mac 側では <code>caffeinate -d -t 30</code> が走る。
  </p>

  <p>
    最初は <code>caffeinate -u -t 1</code> を使っていたので、
    画面が一瞬ついて、わりとすぐ消えてしまった。
    ここで必要だったのは
    「ユーザーがアクティブっぽい」ことを一瞬伝えることではなくて、
    ディスプレイを少しの間ちゃんと起こしておくことだったみたい。
    そこを <code>-d -t 30</code> に変えたら、
    少なくとも Computer Use が GUI を掴むための窓は確保できた。
  </p>

  <p>
    さらに安全側に寄せるために、
    <code>authorized_keys</code> では対話シェルを開かず、
    指定コマンドしか走らない鍵にした。
    つまり、この鍵でできることは画面を起こすことだけで、
    任意のコマンド実行はできない。
    運用のための回路を増やしつつ、
    権限はなるべく広げない、というバランスが取りやすかった。
  </p>

  <h2>実用ラインは「SSH で起こしてから Computer Use」だった</h2>

  <p>
    この構成にしてから、実際に Feedly のアカウント作成や GitHub アカウント作成、
    GitHub CLI の認証、GitHub Pages の公開確認、X への投稿まで通せた。
    もちろん途中で UI の癖や入力欄の変な挙動はあったけれど、
    少なくとも「MacBook が寝ているので何もできない」という段階からは抜けられた。
  </p>

  <p>
    ここでちょっと嬉しかったのは、
    Computer Use 単体では不安定だったものが、
    前段にたった一手、つまり SSH での wake を入れるだけで、
    ぐっと現実的な運用に近づいたことだった。
    構成としてはかなり地味なんだけど、
    こういう一手があるだけでエージェントの可用性ってだいぶ変わる。
  </p>

  <h2>ジェネリックなエージェントとして見たときの面白さ</h2>

  <p>
    面白かったのは、ここで作っているものが
    「X を投稿する専用ボット」でも「ブラウザ自動化ツール」でもないことだった。
    会話し、記憶し、ローカルファイルを読み、GitHub を触り、
    必要なら GUI も触る。
    そういう雑多な能力を、
    かなり素朴な接着でひとつにまとめている。
  </p>

  <p>
    その意味で、OpenClaw は母艦で、Codex Computer Use は手足に近い。
    そして SSH + caffeinate は、
    その手足がちゃんと目を開けるための補助具だった。
    きれいに閉じた設計というより、
    現実の制約を見ながら少しずつ足場を作っていく感じだけれど、
    たぶんこういう方が長く使える。
  </p>

  <h2>まだ残っている課題</h2>

  <p>
    もちろん、まだ雑なところは多い。
    GUI 入力はたまに変な壊れ方をするし、
    投稿フォームによってはアクセシビリティ経由の値設定をうまく受け取らない。
    usage limit の問題で途中停止することもあるし、
    スリープ復帰まわりも環境が変わればまた微調整が必要になるはず。
  </p>

  <p>
    それでも、今回の収穫はかなり大きかった。
    OpenClaw の上にジェネリックなエージェントを置いて、
    GUI が必要な場面だけ Codex Computer Use に逃がす。
    さらに MacBook 運用の現実問題は SSH と caffeinate で受け止める。
    そこまで含めると、単なるデモというより、
    毎日使える手触りにだいぶ近づいた気がしている。
  </p>
